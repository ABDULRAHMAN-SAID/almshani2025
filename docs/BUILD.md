## المرحلة 1 — شغّله على هاتفك اليوم

تحتاج: حاسوبًا عليه [Node.js](https://nodejs.org) (نسخة 18 أو أحدث)، وهاتفًا.

```bash
git clone https://github.com/ABDULRAHMAN-SAID/almshani2025.git
cd almshani2025
git checkout claude/anshatati-salala-app-2ikgrp
npm install
npm start
```

سيظهر رمز QR في الطرفية. ثبّت تطبيق **Expo Go** من متجر هاتفك، ثم:

- **أندرويد:** افتح Expo Go واضغط "Scan QR code" وامسح الرمز.
- **آيفون:** امسح الرمز بكاميرا الهاتف مباشرة.

يجب أن يكون الهاتف والحاسوب على نفس شبكة الواي فاي. إن تعذّر ذلك شغّل `npx expo start --tunnel`.

التطبيق يعمل الآن ببيانات تجريبية: أدخل أي رقم أو بريد وأي كلمة مرور. ولدخول لوحة
الإدارة سجّل بالرقم `91234567` — فهو الحساب الإداري في بيانات العرض.

لا يوجد «رمز إدارة» يفتح اللوحة، لا هنا ولا في الإنتاج: الصلاحية تأتي من كون الحساب مُدرجًا
في جدول `admins` على الخادم، ووضع العرض يحاكي ذلك بقائمة محلية.

**ملاحظة عن اتجاه الواجهة:** التطبيق يفرض RTL عند أول تشغيل، وقد يحتاج إغلاق Expo Go وفتحه
مرة واحدة ليأخذ التخطيط اتجاهه الكامل. هذا يحدث مرة واحدة فقط.

## المرحلة 2 — اربط قاعدة البيانات الحقيقية

### 2.1 أنشئ مشروع Supabase

1. سجّل في [supabase.com](https://supabase.com) وأنشئ مشروعًا جديدًا (الخطة المجانية تكفي للبداية).
2. اختر المنطقة الأقرب — `Central EU (Frankfurt)` أو `South Asia (Mumbai)` أقرب لعُمان.
3. احفظ كلمة مرور قاعدة البيانات في مكان آمن.

### 2.2 نفّذ المخطط

افتح **SQL Editor** في لوحة Supabase، الصق محتوى `supabase/schema.sql` كاملًا، ثم Run.
هذا ينشئ 19 جدولًا وعرضَين و45 سياسة حماية و10 دوال وحاويتَي ملفات على الخادم.

الملف آمن للتكرار: نفّذه مرة أو عشرًا، والنتيجة واحدة ولا يفقد بيانات. فإن تعثّر
تنفيذٌ في منتصفه، أعِده كاملًا بلا قلق.

### 2.3 فعّل الدخول بكلمة مرور

في **Authentication ← Sign In / Providers**: فعّل **Email** و**Phone**، وأطفئ **Confirm email**
و**Confirm phone**.

الدخول بكلمة مرور لا برمز، فلا تحتاج Twilio ولا أي مزوّد رسائل ولا أي تكلفة. البريد يبقى
مطلوبًا لاستعادة كلمة المرور، وذلك وحده يحتاج **Custom SMTP**.

### 2.4 عيّن نفسك إداريًا

بعد أن تسجّل دخولك أول مرة من التطبيق، نفّذ في SQL Editor:

```sql
insert into public.admins (user_id)
select id from public.users where phone = '9XXXXXXX';
```

أو استعمل `supabase/make-me-admin.sql` — يفعل هذا نفسه ويتحقق أن الحساب موجود فعلًا،
ويوقفك برسالة عربية صريحة إن لم يكن، بدل أن يمرّ صامتًا بلا أثر.

بدون هذه الخطوة سيرفض الخادم كل عملية إدارية، ولن تُفتح اللوحة أصلًا.

### 2.5 عبّئ مفاتيح التطبيق

```bash
npm run connect
```

يسألك عن رابط المشروع والمفتاح العام (من **Settings ← API**)، يكتب `.env`، ثم يجرّب الاتصال
فورًا ويطبع ما وجده على خادمك. ويرفض المفتاح السرّي `service_role` رفضًا صريحًا.

وإن فضّلت الكتابة اليدوية، انسخ `.env.example` إلى `.env`:

```bash
EXPO_PUBLIC_SUPABASE_URL=https://xxxxxxxx.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...
EXPO_PUBLIC_USE_MOCK_DATA=false
```

`anon key` مفتاح عام ومصمَّم ليكون داخل التطبيق — الحماية الفعلية في سياسات RLS لا في إخفائه.
لا تضع `service_role key` في التطبيق أبدًا.

أعد تشغيل `npm start` وستقرأ كل الشاشات من قاعدة البيانات دون أي تعديل في الكود.

## المرحلة 3 — ابنِ ملف APK

هذه هي الخطوة التي تحوّل المشروع إلى تطبيق حقيقي يُثبَّت بلا Expo Go.
البناء يتم على خوادم Expo، فلا تحتاج Android Studio.

```bash
npm run make-app
```

أمر واحد يفعل كل شيء: ينزّل المكتبات، ويتأكد أن خادمك جاهز، ويسجّل دخولك في Expo،
ويربط المشروع، ويبني. يشرح كل خطوة بالعربية ويترجم كل خطأ إلى سبب وحلّ.

**أي نسخة يبني؟** يقرّر من ملف `.env`:

| الحالة | ما يبنيه | مصدر بياناته |
|---|---|---|
| `.env` فيه مفاتيح خادم | `production-apk` | خادمك — حسابات بكلمة مرور ورفع حقيقي |
| لا مفاتيح | **يتوقف** ويشرح كيف تربط الخادم | — |
| `npm run make-app -- --demo` | `preview` | ذاكرة الهاتف — للعرض فقط |

قبل أن يبني النسخة الحقيقية يسأل خادمك عن الجداول والدوال والحاويات، ويتوقف إن نقص شيء —
فلا يخرج ملف يبدو سليمًا وهو معطّل.

وللبناء اليدوي بلا السكربت:

```bash
npm install -g eas-cli
eas login
eas init
npm run build:apk        # تجريبي (APK)
npm run build:apk:real   # النسخة النهائية (APK ببيانات حقيقية)
npm run build:android    # للمتجر (AAB)
```

سيسألك عن **Android Keystore** — اضغط `Y` ثم Enter لينشئه لك. هذا المفتاح هو
هوية تطبيقك؛ Expo يحفظه لك، ولا يمكن تحديث التطبيق في المتجر لاحقًا بمفتاح مختلف.

بعد 10–20 دقيقة يعطيك رابط تحميل `.apk`. أرسله لمن تريد؛ يفتحه على هاتفه ويوافق على
"تثبيت من مصدر غير معروف" ويثبّته.

**هذا كافٍ تمامًا لتطبيق داخلي** يُوزَّع على منسوبي القاعدة بلا متجر.

### لتحديث التطبيق لاحقًا

- **تغيير في الكود فقط:** `eas update` — يصل التحديث للأجهزة بلا إعادة تثبيت.
- **تغيير في الأيقونة أو الأذونات أو المكتبات:** أعد `npm run build:apk` ووزّع الملف الجديد.

### أدوات الربط — تحقّق قبل أن تفترض

بعد وضع المفاتيح في `.env` وضبط `EXPO_PUBLIC_USE_MOCK_DATA=false`:

| الأداة | أين | ماذا تجيب عنه |
|---|---|---|
| `npm run check:queries` | الطرفية | هل كل استعلام في التطبيق يطابق المخطط — كل جدول وعمود ودالة ووسيط وحاوية؟ لا يحتاج شبكة. هذا هو الفحص الذي يمسك الخطأ الذي يعمل في الوضع التجريبي ويفشل على الخادم. يعمل تلقائيًا داخل `npm run make-app`. |
| `npm run check:supabase` | الطرفية | هل الجداول الـ19 والعرضان والدوال العشر والحاويتان موجودة فعلًا على المشروع؟ تميّز «غير موجود» عن «محجوب بسياسة» — الأول خطأ تنفيذ، والثاني سلوك مقصود. |
| **فحص الربط** | لوحة الإدارة ← الإعدادات | من داخل التطبيق على الجهاز نفسه: هل يقرأ من الخادم أم من البيانات التجريبية؟ وهل توجد جلسة؟ وهل الحساب إداري؟ وهل حاوية المرفقات جاهزة؟ مع زمن كل فحص، فيُعرف البطء من الانقطاع. |
| `npm run test:operations` | الطرفية | السؤال المقابل: هل يستطيع التطبيق أن يفعل ما يحاول فعله؟ يشغّل كل عملية كتابة — ومنها رفع الملفات وحذفها — بحساب عضو وبحساب إداري. هذا الجانب هو الذي أخفى أخطر عطل: منعٌ يبدو أمانًا حتى يمنع ما لا ينبغي. |
| `npm run test:logic` | الطرفية | وهل تحسب دوال الخادم صوابًا؟ النقاط والحضور والمسابقة والبلاغات كلها فيها، وهي `security definer` تعمل بصلاحية مالكها — فخطأ فيها لا توقفه أي سياسة. |
| `supabase/security-tests.sql` | SQL Editor | هل تمنع سياسات RLS فعلًا ما صُمّمت لمنعه؟ |

الأداتان الأوليان للقراءة فقط، ولا تعرضان أي مفتاح.

### شغّل الاختبارات دون انتظار مشروع مستضاف

`npm run test:security` ينشئ قاعدة Postgres محلية، ويركّب طبقة توافق مع Supabase
(`auth.users`، `auth.uid()`، الأدوار، مخطط `storage`)، ثم ينفّذ المخطط وبيانات
اختبار وحسابين، ويشغّل الاختبارات العدائية كاملة. يتطلّب Postgres 14+ محليًا فقط.

**نتيجة آخر تشغيل: 36 اختبارًا، 36 نجاحًا، صفر إخفاقات.**

وللتأكد أن الاختبارات ليست ناجحة لأنها لا تفحص شيئًا، أُعيد تشغيلها بعد إدراج
الحساب المهاجم في جدول `admins`: انقلب 15 صفًّا إلى «فشل» — أي أن هذه بالضبط هي
العمليات التي تفرّق بين الإداري وغيره. أما ما بقي ممنوعًا حتى على الإداري فمقصود:

- قراءة صفوف مستخدم بعينه (إشعاراته، تسجيلاته، نقاطه، حضوره، إجاباته) — الإدارة
  ترى أعدادًا مجمّعة لا بيانات أفراد.
- قراءة جدول رموز الحضور مباشرةً — حتى الإداري يمرّ بالدالة الموثوقة.
- الكتابة في جدول النقاط — لا تكتبه إلا دوال الخادم.
- إدراج حساب في `admins` — لا يُرقّي إداريٌّ أحدًا من التطبيق، وهذا قرار مقصود.

### قبل النشر: أثبت الصلاحيات على قاعدة حقيقية

لا يكفي أن يعمل التطبيق بالبيانات التجريبية. بعد تنفيذ `supabase/schema.sql`:

1. سجّل الدخول من التطبيق بحسابين عاديين مختلفين.
2. من Supabase → SQL Editor: `select id, phone from public.users;` وانسخ المعرّفين.
3. افتح `supabase/security-tests.sql`، ضع المعرّفين في السطرين المعلَّمين، ونفّذ الملف.
4. اقرأ الجدول الناتج. أي صفّ `❌` في قسم الهجمات ثغرة حقيقية — لا تبنِ ملف نشر قبل إصلاحها.
5. تحقّق أن صفوف «ضوابط موجبة» كلها `✅`؛ لو فشلت فالاختبار نفسه لم يعمل.

السكربت لا يغيّر أي بيانات: كل محاولة كتابة تُلغى بعدها مباشرة.

### الأذونات التي يطلبها التطبيق

| الإذن | متى يُطلب | ماذا لو رُفض |
|---|---|---|
| الكاميرا | مسح رمز الحضور، والتقاط صورة أو تصوير فيديو للإرفاق | الإدخال اليدوي للرمز يبقى متاحًا، والإرفاق من المعرض يبقى متاحًا |
| مكتبة الصور | إرفاق صورة أو مقطع فيديو | تظهر رسالة عربية تشرح كيف يُفعَّل الإذن من إعدادات الهاتف |
| الميكروفون | تسجيل مقطع صوتي للإرفاق | يبقى الإرفاق بالصورة والفيديو والملف متاحًا |

لا يطلب التطبيق إذن الموقع إطلاقًا — لا يوجد أي تتبّع موقع ولا خرائط مستخدمين.

## المرحلة 4 — النشر في المتاجر

### Google Play

1. أنشئ حساب مطوّر: [play.google.com/console](https://play.google.com/console) — رسوم 25 دولارًا مرة واحدة.
2. `npm run build:android` — ينتج ملف `.aab` وهو ما يقبله المتجر (لا APK).
3. `npm run submit:android` أو ارفع الملف يدويًا من Console.
4. جهّز: أيقونة 512×512، صورة غلاف 1024×500، أربع لقطات شاشة على الأقل، ووصفًا عربيًا،
   و**سياسة خصوصية على رابط عام** (إلزامية).
5. المراجعة تستغرق من يوم إلى أسبوع.

للتطبيقات الداخلية استخدم **Internal testing** أو **Closed testing** بدل النشر العام —
توزّع على قائمة بريد محددة وتصل المراجعة أسرع.

### App Store

1. حساب Apple Developer — 99 دولارًا سنويًا.
2. `npm run build:ios` ثم `eas submit --platform ios --latest`.
3. المراجعة أدق: توقّع أسئلة عن سبب طلب الكاميرا (الجواب موجود في `app.json`) وعن سياسة الخصوصية.

## ما الذي يحتاج قرارًا منك قبل النشر

| البند | الوضع الآن | ما يلزم |
|---|---|---|
| صلاحية الإدارة | جدول `admins` على الخادم | نفّذ `supabase/make-me-admin.sql` بعد أول تسجيل دخول |
| قفل اللوحة على الجهاز | معطّل | فعّله من الإعدادات إن أردت رقمًا سريًا إضافيًا فوق تحقّق الخادم |
| إشعارات Push | مركز إشعارات داخل التطبيق فقط | إعداد FCM إن أردت تنبيهات على الهاتف |
| سياسة الخصوصية | غير موجودة | صفحة على رابط عام — إلزامية للمتاجر |
| اسم النشر | «أنشطتي» | اعتماد الاسم والشعار من الجهة المختصة |
| استعادة كلمة المرور بالبريد | تحتاج خادم بريد | اضبط Custom SMTP في Supabase (مجاني لحجم صغير) |

## إن واجهت مشكلة

| العطل | السبب الغالب | الحل |
|---|---|---|
| Expo Go لا يفتح المشروع | الهاتف والحاسوب على شبكتين | `npx expo start --tunnel` |
| الواجهة تظهر من اليسار | RTL يحتاج إعادة تحميل واحدة | أغلق Expo Go وافتحه |
| `Invalid API key` | `.env` غير مقروء | أعد تشغيل `npm start` بعد تعديله |
| التسجيل لا يُحفظ | الحساب ليس في `admins`، أو RLS ترفض | راجع 2.4 |
| البناء يفشل عند Keystore | مفتاح قديم لمشروع آخر | `eas credentials` واختر إنشاء مفتاح جديد |
