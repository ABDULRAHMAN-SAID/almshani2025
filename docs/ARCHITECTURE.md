# أنشطتي | قاعدة صلالة الجوية — المعمارية التقنية

> تطبيق داخلي غير سري لتنظيم الأنشطة العامة، المسابقات، المحاضرات، الرياضة، التوعية، والتقويم السنوي.
> **لا يحتوي على أي معلومة عسكرية سرية أو تشغيلية أو رتب أو أرقام عسكرية.**

---

## 1. نظرة معمارية عامة

| الطبقة | التقنية |
|---|---|
| التطبيق | React Native + Expo (SDK 51) |
| اللغة | TypeScript |
| التنقل | Expo Router (ملفات = مسارات) |
| الحالة الخادمية | TanStack Query (React Query) |
| الحالة المحلية | Zustand |
| الخلفية (Backend) | Supabase (Postgres + Auth + Storage) |
| الإشعارات | Firebase Cloud Messaging (مرحلة لاحقة) |
| الخطوط | Tajawal (عربي احترافي، عبر Expo Google Fonts) |
| الأيقونات | @expo/vector-icons (بدون إيموجي) |

### مبدأ Clean Architecture

```
app/                  → المسارات فقط (Expo Router) — لا منطق أعمال هنا
src/
  components/         → عناصر واجهة قابلة لإعادة الاستخدام (بلا منطق أعمال)
  features/           → منطق كل ميزة (مسابقات، محاضرات، تقويم...) لاحقًا
  services/           → الاتصال بـ Supabase / Mock Data / Auth
  store/              → Zustand stores (auth, ui)
  hooks/              → React Query hooks + hooks عامة
  types/              → Models & Types مشتركة
  utils/              → دوال مساعدة (تواريخ، تنسيق نص عربي...)
  constants/          → Design Tokens (ألوان، مسافات، خطوط، تصنيفات)
assets/
  images/logo/        → مكان شعار سلاح الجو (قابل للاستبدال بسهولة)
supabase/
  schema.sql          → مخطط قاعدة البيانات الكامل
```

كل شاشة في `app/` هي "غلاف" رفيع يستدعي مكونات من `src/components` وبيانات من `src/hooks` — لا تُكتب استعلامات Supabase أو تنسيقات ثابتة داخل ملفات `app/` مباشرة.

### مصدر البيانات القابل للتبديل

كل الشاشات تقرأ البيانات عبر `src/services/*` و`src/hooks/*` فقط. حاليًا `services` تُرجع **Mock Data عربي واقعي** (بدون Lorem Ipsum)، وهي مبنية بنفس شكل استجابة Supabase تمامًا، بحيث يكون التبديل لاحقًا إلى Supabase الحقيقي بتغيير سطر واحد (`USE_MOCK` في `src/services/config.ts`) دون تعديل أي شاشة.

  ولا تحتوي على أي شكل نجمي. تُستعمل عبر `PatternOverlay` بشفافية 6–8٪ فوق الأسطح الكحلية.
- **أغلفة الأقسام:** `assets/images/covers/cover-<التصنيف>.png` — عشرة أغلفة مرسومة، لكل تصنيف غلاف
  بتدرّج لونه وفوقه النقشة ورمز القسم. تُقرأ من `src/constants/covers.ts` وتظهر في بطاقة النشاط،
  بطاقة النشاط القادم، غلاف شاشة التفاصيل، رأس شاشة القسم، مقال التوعية، وصفوف القوائم.
- **التدرّجات:** `expo-linear-gradient` بتدرّج كحلي واحد (`primaryLight → primary → primaryDark`) في شاشة البداية،
  الشريط العلوي للرئيسية، وبطاقة النشاط القادم؛ وتدرّج بلون القسم في أغلفة بطاقات الأنشطة.
- **الشريط العلوي (`HeaderBand`):** شريط كحلي بزوايا سفلية دائرية يحمل الشعار والترحيب ورصيد النقاط،
  وتتداخل معه شبكة الأقسام من الأسفل لإعطاء إحساس بالعمق بدل الشكل المسطّح.

المبدأ: **الزخرفة خلفية لا موضوع** — تبقى خافتة دائمًا ولا تنافس المحتوى ولا تُستخدم فوق النصوص الطويلة.

كل الشاشات تلتزم بتدرّج واضح: **عنوان → معلومة مهمة (تاريخ/حالة) → وصف → زر**، بدون تكديس بصري.

## 5. مخطط قاعدة البيانات (Supabase / Postgres)

انظر `supabase/schema.sql` للنص الكامل القابل للتنفيذ. ملخص الجداول:

- **users** — id, phone, full_name, created_at *(بدون رتبة/رقم عسكري/جهة عمل)*
- **activities** — id, title, description, category, cover_image, date, start_time, end_time, location, capacity, registration_status, registration_deadline, is_annual, created_at
- **registrations** — id, user_id, activity_id, status, registered_at (unique: user_id+activity_id)
- **announcements** — id, title, description, type, published_at
- **awareness_articles** — id, title, summary, content, category, image, published_at
- **notifications** — id, user_id, title, body, read, created_at
- **activity_results** *(اختياري، بعد انتهاء المسابقة)* — activity_id, rank, winner_name, note
- **points_transactions** — user_id, reason (حضور/مشاركة/سؤال ثقافي)، points، activity_id?، created_at
- **activity_checkins** — user_id, activity_id, code, checked_in_at (فريد لكل مستخدم+نشاط)
- **weekly_quizzes / quiz_questions / quiz_answers** — الأسئلة الثقافية الأسبوعية والإجابات — راجع القسم 10
- **app_contact** — صفّ واحد ببيانات التواصل الرسمية (قراءة عامة، كتابة إدارية)
- **user_messages** — رسائل المستخدمين إلى الإدارة: user_id, user_name, kind, subject, body, attachments, status, reply_body, replied_at
- **discussion_groups / group_posts / group_post_reports** — المجموعات النقاشية المُدارة ومشاركاتها وبلاغاتها — راجع القسم 11

جميع الجداول محمية بـ Row Level Security: المستخدم يقرأ بياناته فقط في `registrations`/`notifications`، والجميع يقرأ `activities`/`announcements`/`awareness_articles` (قراءة عامة، كتابة للإدارة فقط عبر Service Role).

### الأمور التشغيلية

| الأمر | كيف يعمل |
|---|---|
| **رفع الصور** | `expo-image-picker` للاختيار أو الالتقاط بالكاميرا، و`uploadService` للرفع. في وضع البيانات التجريبية يُرجع المسار المحلي، وفي الإنتاج يرفع إلى حاوية `activity-images` (أغلفة الإدارة) أو `app-media` (مرفقات المستخدمين) ويعيد الرابط العام. الحد 3 ميجابايت. |
| **رفع الفيديو** | اختيار من المعرض أو تصوير مباشر، بسقف 60 ثانية و25 ميجابايت. يُعرض بمشغّل `expo-av` بأزرار تحكم أصلية. |
| **التسجيل الصوتي** | `useAudioRecorder` فوق `expo-av`: زر تسجيل بمؤقّت وإيقاف تلقائي عند دقيقتين، وإلغاء يحذف المقطع. الميكروفون يُحرَّر في كل مسار خروج بما فيه مغادرة الشاشة أثناء التسجيل. |
| **إرفاق الملفات** | `expo-document-picker` لمستندات PDF/Word/Excel/نص وصور، بحد 10 ميجابايت. الملف يُفتح بتطبيق الجهاز عبر `Linking`. |
| **الاتصال والمراسلة** | شاشة «تواصل معنا» تفتح المكالمة والرسالة النصية والواتساب والبريد عبر `Linking` مع فحص التوفّر أولًا. ومراسلة الإدارة داخل التطبيق عبر `messageService`. |
| **مسح رمز QR** | `expo-camera` مع طلب الإذن تلقائيًا عند فتح الشاشة. إن رُفض الإذن نهائيًا يُفتح إعدادات الهاتف، ويبقى الإدخال اليدوي متاحًا دائمًا كبديل. |
| **الاتصال** | `useConnection` عبر NetInfo، مربوط بـ `onlineManager` في React Query — فتتوقف المحاولات عند الانقطاع وتُستأنف تلقائيًا. `OfflineBanner` يظهر أعلى التطبيق. |
| **أخطاء الخادم** | `toArabicMessage` يترجم أخطاء Postgres وSupabase وHTTP إلى رسائل عربية. **كل** نداء خدمة في الشاشات له `catch` يعرضها. |
| **إعادة المحاولة** | استعلامات React Query تعيد المحاولة مرتين بتباعد متزايد، و`QueryState` يعرض زر «إعادة المحاولة» عند الفشل. |
| **إرسال الإشعارات** | `broadcast_notification` تكتب صفًا لكل مستخدم داخل الخادم. الفشل يظهر كرسالة، ولا يُترك الزر صامتًا. |
| **فحص الربط** | `npm run check:supabase` من الطرفية يفحص الجداول والدوال والحاويات، وشاشة «فحص الربط» في اللوحة تفحص من الجهاز نفسه: المصدر، الجلسة، الصلاحية، والمرفقات، مع زمن كل فحص. |
| **إدارة النقاش** | قفل المجموعة، تثبيت مشاركة، حذف أي مشاركة، وقراءة البلاغات — كلها من حساب إداري فقط، وتفرضها سياسات RLS لا الواجهة. |

### الوصول للوحة الإدارة

**لا يوجد رمز إدارة مشترك.** مصدر الصلاحية الوحيد هو جدول `admins` على الخادم.

المسار: رقم أو بريد + كلمة مرور ← اللوحة تسأل `is_admin()` ← تُفتح أو
تُرفض. من ليس في الجدول يرى «هذا الحساب ليس إداريًا» ولا يُفتح له شيء، ومن هو
فيه لا يُطلب منه أي رمز إضافي.

`app/admin/_layout.tsx` يغطّي **كل** شاشة تحت `/admin` دفعة واحدة، فلا يمكن فتح
شاشة إدارية برابط مباشر. ووضع الإدارة لا يُحفَظ في التخزين عمدًا: يُعاد سؤال
الخادم في كل جلسة.

**قفل الجهاز (اختياري، مطفأ افتراضيًا):** رقم من 4 إلى 6 خانات يُضبط من إعدادات
اللوحة، ويُطلب بعد أن يقرّ الخادم الصلاحية. مفيد على جهاز مشترك. لا يُرسَل إلى
أي مكان، ولا يمنح صلاحية بذاته — `unlockWithPin` ترفض العمل ما لم يكن الخادم قد
أقرّ الصلاحية أولًا.

**لماذا لا يُدار جدول `admins` من داخل التطبيق:** لو أمكن ذلك لصار فتح اللوحة على
جهاز واحد كافيًا لترقية حسابات أخرى. شاشة «الحسابات الإدارية» تقرأ القائمة من
الخادم وتعرضها بأرقام مقنّعة، والإضافة والإزالة من Supabase بيد مالك المشروع.

ويبقى المدخل المخفي كما هو لمن سجّل دخوله كمستخدم: ضغطة مطوّلة على اسم التطبيق
أسفل شاشة «حسابي» — وهي اختصار للوصول، لا صلاحية.

### ماذا تفعل لوحة التحكم
| التبويب | المحتوى |
|---|---|
| نظرة عامة | تسع بطاقات إحصائية + سبعة إجراءات سريعة (منها الرسائل الواردة والمجموعات النقاشية) + أقرب الأنشطة |
| الأنشطة | بحث وفلترة على كل الأنشطة، وكل صف يفتح شاشة إدارة النشاط |
| المحتوى | الإعلانات (نشر وحذف) + مدخل المسابقة الثقافية + مدخل المحتوى التوعوي |
| المشاركون | قائمة المتصدرين ومجاميع النقاط — بلا أي بيانات شخصية |
| الإعدادات | مفاتيح التشغيل، الحسابات الإدارية، الإشعارات المرسلة، وسجل العمليات |

**إدارة نشاط واحد** (`admin/activity/[id]`): تعديل كل الحقول، تغيير حالة التسجيل،
عرض نسبة الإشغال والمقاعد المتبقية، توليد/حفظ رمز الحضور، إدخال نتائج المراكز
الثلاثة، معاينة الشاشة كما يراها المستخدم، وحذف النشاط بتأكيد.

### إعدادات اللوحة — مفاتيح تغيّر سلوك التطبيق فعليًا
| الإعداد | أثره |
|---|---|
| قفل الجهاز | قفل رقمي اختياري على هذا الجهاز فوق تحقق الخادم — مطفأ افتراضيًا، ولا يمنح صلاحية |
| التسجيل في الأنشطة | عند الإيقاف تُرجع `canRegister` رفضًا فيختفي زر التسجيل من كل نشاط |
| السؤال الثقافي الأسبوعي | عند الإيقاف تُرجع `fetchCurrentWeeklyQuiz` قيمة `null` فتختفي البطاقة والشاشة |
| نظام النقاط | عند الإيقاف تُمنح صفر نقاط على الحضور وعلى الإجابات الصحيحة |
| قيمة النقاط لكل عملية | 5 / 10 / 15 / 20 — تُقرأ في `checkinService` و`quizService` |
| المجموعات النقاشية | عند الإيقاف تختفي من الشبكة الرئيسية ومن «حسابي»، وتُغلق شاشة المجموعات — والمحتوى يبقى محفوظًا |
| مراسلة الإدارة | عند الإيقاف تُغلق شاشة الكتابة ويختفي مدخلها، وتبقى الرسائل والردود السابقة قابلة للقراءة |
| الحالة الافتراضية للتسجيل | تُملأ مسبقًا في نموذج «إضافة نشاط» |

**سجل العمليات**: كل إضافة أو تعديل أو حذف أو تغيير إعداد يُسجَّل باسمه ووقته
(آخر 100 عملية)، فتبقى التغييرات قابلة للمراجعة.

**الحسابات الإدارية**: تُقرأ من جدول `admins` على الخادم وتُعرض بأرقام مقنّعة
(`9•••4567`). الإضافة والإزالة من Supabase لا من التطبيق. سياستان تحكمان ذلك:
`admins read all for admins` لقراءة القائمة، و`users read admin peers` لقراءة
أسماء وأرقام الإداريين وحدهم — لا بقية المستخدمين.

### الصلاحية على الخادم
الصلاحية تُقرَّر هنا وحدها، ولا يوجد في التطبيق ما يمنحها. في `schema.sql`:

- جدول `admins` + دالة `is_admin()`، وكل كتابة إدارية (أنشطة، إعلانات، توعية،
  مسابقة) محكومة بسياسة RLS تتحقق منها.
- `set_check_in_code` / `get_check_in_code` / `admin_registration_counts` /
  `broadcast_notification` دوال `security definer` ترفض الاستدعاء من غير إداري.
- **رمز الحضور في جدول `activity_checkin_codes` المستقل** وليس عمودًا في
  `activities`؛ الأخير مقروء للجميع، ولو كان الرمز فيه لاستطاع أي مستخدم قراءته
  ومنح نفسه نقاط حضور دون أن يحضر. الجدول المستقل عليه RLS بلا أي سياسة قراءة،
  فلا يصل إليه العميل إطلاقًا.
- الإجابة الصحيحة للسؤال الثقافي لا تصل إلى تطبيق المستخدم أبدًا: القراءة العامة
  عبر `quiz_questions_public`، والإدارة وحدها ترى `correct_option_index`.

### إثبات الصلاحيات — لا افتراضها

`supabase/security-tests.sql` سكربت اختبارات عدائية يُنفَّذ على قاعدة البيانات
الحقيقية بعد المخطط. يأخذ معرّفي حسابين عاديين، وينتحل هوية كل منهما عبر
`request.jwt.claims` — نفس المسار الذي يقرأ منه `auth.uid()` — ثم يجرّب:

قراءة رسائل مستخدم آخر وإشعاراته وتسجيلاته ونقاطه، قراءة جدول الأسئلة بإجاباته،
قراءة رموز الحضور مباشرةً وعبر الدالة، تعديل نقاط غيره، منح نفسه نقاطًا، تسجيل
حضور بلا رمز، إدراج نفسه في `admins`، إضافة نشاط أو إعلان، استدعاء
`broadcast_notification` و`set_check_in_code` و`reply_to_message`، تغيير بيانات
التواصل، حذف مشاركة ليست له أو تثبيتها، النشر باسم غيره، النشر في مجموعة مقفلة،
وحذف ملف رفعه غيره.

كل محاولة كتابة تُلغى بعدها مباشرة، فالسكربت لا يغيّر شيئًا. ويتضمّن **ضوابط
موجبة** (قراءة المستخدم صفَّه هو) — فلو فشلت، فالاختبار نفسه لم يعمل ولا يُوثق
بنتيجة بقية الصفوف. الإخفاقات تظهر في أعلى الجدول الناتج.

بعد كل مرحلة: تشغيل `npm run typecheck`، اختبار التنقل، اختبار RTL، اختبار الاستجابة، ثم الانتقال للمرحلة التالية — كما هو مطلوب.

## 8. الخصوصية والأمان (مطبّقة منذ البداية)

- لا رتب، لا أرقام عسكرية، لا جهة عمل — الحقل غير موجود أصلاً في `types/models.ts`.
- لا مشاركة أرقام هواتف بين المستخدمين — لا يوجد عمود هاتف في أي جدول نقاش أو رسائل، والإدارة ترى الاسم فقط.
- **لا رسائل خاصة بين المستخدمين ولا دردشة فورية.** ما يوجد قناتان معلنتان فقط:
  1. **مراسلة الإدارة** — قناة رسمية باتجاه واحد: المستخدم يكتب إلى قسم الأنشطة والقسم يردّ. سياسة RLS تمنع أي مستخدم من قراءة رسالة غيره، ولا يستطيع أحد كتابة رد باسم القسم.
  2. **المجموعات النقاشية المُدارة** — لوحات نقاش عامة حول أنشطة، تُنشئها الإدارة وحدها، وكل مشاركة فيها يراها الجميع وتراجعها الإدارة. لا قائمة أعضاء، ولا مسار مراسلة فردية، ويمكن قفل المجموعة أو إيقاف الخاصية كلها من الإعدادات.
  هذا توسيع مقصود للقيد الأصلي «لا دردشة»، طُلب صراحةً؛ ولذلك بُني مُدارًا ومكشوفًا للجميع بدل أن يكون مراسلة خاصة.
- لا Location Tracking ولا خرائط مستخدمين.
- قسم الرماية لا يحتوي حقولًا لأي معلومة تقنية/تشغيلية — فقط تاريخ، وقت، تسجيل، ملاحظات عامة.
- المحتوى التوعوي (أمني/سلامة/مخدرات) عام بالكامل، لا تفاصيل تشغيلية.

## 10. نظام النقاط والمسابقة الثقافية الأسبوعية

ميزة إضافية طُلبت بعد المرحلة 1: تحفيز الحضور والمشاركة بنقاط، مع أسئلة ثقافية أسبوعية.

### قواعد منح النقاط
قيمة موحّدة وبسيطة لكل الأسباب — **10 نقاط**، بلا تفاوت، لتبسيط الفهم للمستخدم ولسهولة تعديلها لاحقًا من الإدارة:

| السبب | النقاط | آلية التحقق |
|---|---|---|
| حضور محاضرة | 10 | رمز حضور (QR أو كود يُدخل يدويًا) يُعرض في القاعة وقت الفعالية |
| المشاركة في نشاط عام | 10 | نفس آلية رمز الحضور |
| إجابة صحيحة على سؤال ثقافي أسبوعي | 10 لكل سؤال | تحقّق فوري داخل التطبيق |

**لماذا رمز حضور وليس تسجيلًا تلقائيًا؟** حتى لا تُمنح النقاط لمجرد "التسجيل" في نشاط دون حضوره فعليًا — هذا قرار تصميمي لضمان نزاهة النظام. الإدارة تعرض الرمز (QR) على شاشة/لوحة في مكان الفعالية، والمستخدم يمسحه من داخل التطبيق؛ يوجد دائمًا خيار **إدخال الرمز يدويًا** كبديل عند تعذّر المسح أو عدم توفر كاميرا.

### الشاشات
- **السؤال الثقافي الأسبوعي**: بطاقة تعريفية في الرئيسية (نفس مستوى بروز "توعية اليوم") + شاشة `app/quiz.tsx` لعرض أسئلة الأسبوع (3 أسئلة، تصنيفات: تاريخ عمان/جغرافيا/علوم/ثقافة عامة كما في المواصفة الأصلية)، مع نتيجة فورية لكل سؤال (صح/خطأ + النقاط المكتسبة) وملخص ختامي.
- **تسجيل الحضور**: `app/check-in.tsx` — ماسح QR (`expo-camera`) + إدخال يدوي كبديل دائم.
- **رصيد النقاط والسجل**: بطاقة صغيرة في الرئيسية وصف الملف الشخصي، وشاشة `app/points-history.tsx` بكل حركة (السبب، النقاط، التاريخ).
- **قائمة المتصدرين**: `app/leaderboard.tsx` — الاسم والمجموع فقط (بدون رقم الهاتف، التزامًا ببند الخصوصية).

### قاعدة البيانات
جداول جديدة في `supabase/schema.sql`: `points_transactions`، `activity_checkins` (+ عمود `check_in_code` على `activities`)، `weekly_quizzes`، `quiz_questions`، `quiz_answers`. **قرار أمني مهم**: العميل لا يقرأ أبدًا `correct_option_index` مباشرة (يقرأ عبر `quiz_questions_public` التي تخفيه)، والتحقق من الإجابة ومنح النقاط يتمّان فقط داخل دالتين موثوقتين على الخادم (`submit_quiz_answer`, `submit_check_in`) — لا يمكن لأي عميل (حتى لو عدّل الطلبات يدويًا) منح نفسه نقاطًا مباشرة. قائمة المتصدرين تُقرأ عبر `leaderboard_view` العلني (اسم + مجموع فقط).

### الحالة الحالية
في وضع البيانات التجريبية (`USE_MOCK_DATA=true`) يعمل كل ما سبق فعليًا بمحاكاة صادقة لهذا المنطق (بيانات وهمية + رمز حضور تجريبي معروف)، بحيث يمكن تجربة التدفق الكامل قبل ربط Supabase الحقيقي.

## 11. المرفقات والمجموعات النقاشية ومراسلة الإدارة

### طبقة الوسائط (`src/services/uploadService.ts`)

أداة رفع واحدة تخدم كل الشاشات:

| النوع | من أين | الحد الأقصى |
|---|---|---|
| صورة | المعرض أو الكاميرا مباشرة | ٣ ميجابايت |
| فيديو | المعرض أو تصوير مباشر (≤ ٦٠ ثانية) | ٢٥ ميجابايت |
| صوت | تسجيل داخل التطبيق (≤ دقيقتين) | ٨ ميجابايت |
| ملف | مستندات PDF/Word/Excel/نص وصور | ١٠ ميجابايت |

- الإذن يُطلب عند أول استخدام؛ رفض الإذن يظهر كرسالة عربية واضحة، والإلغاء ليس خطأ.
- في وضع البيانات التجريبية يُرجع المسار المحلي فتعمل المعاينة والتشغيل بلا خادم؛ وعند الربط تُرفع إلى حاوية `app-media`.
- حاويتان منفصلتان: `activity-images` لأغلفة الإدارة (كتابة إدارية فقط)، و`app-media` لمرفقات المستخدمين (كتابة لكل مستخدم مسجَّل، وحذف لصاحب الملف أو الإدارة).

المكوّنات: `MediaField` (شريط الإرفاق والتسجيل)، `AttachmentList` (عرض المرفقات)، `AudioPlayer` (تشغيل المقاطع الصوتية). التسجيل الصوتي في `src/hooks/useAudioRecorder.ts`، ويحرّر الميكروفون في كل مسار خروج بما فيه مغادرة الشاشة أثناء التسجيل.

### مراسلة الإدارة

`app/compose.tsx` → `app/my-messages.tsx` → `app/admin/inbox.tsx`. نوع الرسالة (اقتراح/طلب/استفسار/ملاحظة)، موضوع، نص، ومرفقات. الحالة تنتقل: جديدة ← مقروءة ← تم الرد. الرد يمرّ عبر الدالة الموثوقة `reply_to_message` التي تكتب الرد وتُرسل إشعارًا لصاحب الرسالة، ولا تعمل إلا لحساب إداري.

### المجموعات النقاشية المُدارة

`app/groups/index.tsx` → `app/groups/[id].tsx`، والإدارة في `app/admin/groups.tsx` و`app/admin/new-group.tsx`.

- المجموعة تُنشئها الإدارة فقط؛ جمهورها إما «الجميع» أو «المسجّلون في نشاط» — والقيد الثاني تفرضه سياسة `posts insert own` على الخادم بالتحقق من جدول التسجيلات، لا في الواجهة وحدها.
- الإدارة تقفل المجموعة (قراءة بلا كتابة)، وتثبّت مشاركة، وتحذف أي مشاركة؛ والمستخدم يحذف مشاركته هو.
- الإبلاغ عن مشاركة يمرّ عبر `report_group_post` مع قيد فرادة `(post_id, reporter_id)` فلا يستطيع أحد رفع عدّاد البلاغات على مشاركة لا تعجبه، والبلاغات تُقرأ من حساب إداري فقط.
- عدّاد المشاركات يُحسب بمُشغِّل (trigger) على الخادم لا في العميل.
- مفتاح `discussionEnabled` في إعدادات اللوحة يُخفي الخاصية من التطبيق كليًا مع بقاء المحتوى محفوظًا.

### بيانات التواصل

`app/contact.tsx` تفتح الاتصال والرسالة النصية والواتساب والبريد عبر `Linking`، وتقول بوضوح إن لم تكن القناة متاحة على الجهاز. البيانات تُحرَّر من `app/admin/contact.tsx` وتُخزَّن في صفّ `app_contact` الذي يقرأه الجميع — فلا تبقى التعديلات حبيسة جهاز المسؤول. لا يظهر في هذه الشاشة أي رقم شخصي لمستخدم؛ خط القسم فقط.
